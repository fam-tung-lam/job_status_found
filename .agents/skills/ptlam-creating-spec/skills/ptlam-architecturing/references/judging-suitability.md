# Judging Suitability

This file covers the judging branch: rebuilding the needs and decisions behind
an existing architecture or proposal, the verdict table, and old rules of thumb
to re-check.

## Review the thinking, not the picture

Most of a review is finding out whether the authors understood the job the
system must do and made their trade-offs on purpose. Rebuild, from their
documents and answers, the needs, the alternatives they saw, the trade-offs they
accepted, and the business need each trade-off served.

Every architecture has something to criticize. A finding counts only when a
trade-off is misaligned with a stated need, was not conscious, or rests on a
stale assumption. Do not review with an agenda for a product, pattern, or
vendor.

## Verdict

| Evidence                                                          | Verdict                                                                 |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------- |
| The needs are unknown or unstated                                 | Cannot judge; return the needs question before any finding              |
| Needs known, trade-offs conscious and aligned with them           | Suitable; list its liabilities as accepted costs                        |
| Needs known, a trade-off unconscious or misaligned                | Not yet suitable; name the trade-off, the need, and the smallest change |
| Needs changed since the design: size, lifespan, next requirements | Suitable then; re-decide now against the new numbers                    |

A quick, cheap design built with a limited skill set has real qualities. Ask
what the next requirements, expected size, and lifespan are before proposing
more structure, and let the answer decide.

## Re-check old rules of thumb

A rule that was right five years ago can be wrong today. Check the current
technology and platform before applying any of these:

| Rule of thumb                          | Check first                                                        |
| -------------------------------------- | ------------------------------------------------------------------ |
| One shared database is a bottleneck    | Whether the store is a managed, horizontally scaled cloud database |
| Everything must scale out              | Whether current data fits one large node's memory                  |
| A monolith cannot be maintained        | Whether it is modular at design time                               |
| A big ball of mud is a mistake         | Whether speed, cost, and available skill were the constraints      |
| Cloud native is best practice          | Whether the business, not the resume, needs the property           |
| Native always beats cross-platform     | Whether the measured users notice the fidelity difference          |
| A library must never take a dependency | Whether the consumers already carry it                             |
| Real time beats batch                  | Whether any consumer acts inside the batch window                  |
| Offline-first is mandatory             | Whether measured sessions run without connectivity                 |
| A CLI must not need a config file      | Whether repeated invocations carry the same flags                  |

Text generated by a tool is a starting point; the review adds the reasoning on
top or adds nothing.

Finish when the verdict names the needs it was judged against, every finding
ties a trade-off to a need, and every applied rule was checked against the
current technology and platform.
